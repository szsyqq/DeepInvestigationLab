## 项目路径约定

| 用途 | 路径 | 说明 |
|------|------|------|
| 底稿（权威源） | `底稿/YYYY-MM-DD_公司/index.html` | 改文章只改这里 |
| 发布版 | `portal/reports/<key>/index.html` | 底稿改完后复制到这里 |
| 门户首页 | `portal/index.html` | **由 `scripts/build-portal.py` 自动生成，不手动编辑** |
| 数据源 | `portal/reports.json` | 新增报告时在此文件最前面加一条记录 |
| 模板 | `portal/template.html` | 门户固定结构的权威源，不手动改卡片区 |
| 生成脚本 | `scripts/build-portal.py` | 从 JSON 数据源自动生成完整首页 |
| 版本归档 | `版本归档/公司_YYYY-MM-DD[_描述]/index.html` | 每次实质修改前存旧版 |

## 输出质量审查清单

> 在推送发布前执行。对应技能生产流程第 8 步「输出质量审查」。

### A. 中文语言审核

逐项检查，全部通过方可发布：

| # | 检查项 | 标准 | 通过 |
|---|--------|------|------|
| 1 | **句子通顺** | 无病句、无英文式长句嵌套、无生硬翻译腔。出声读一遍，卡顿处即修改。 | ☐ |
| 2 | **故事线清晰** | 导语用矛盾钩住读者，每章围绕一个核心追问展开，尾声闭环回扣。一章读完应能一句话复述该章在讲什么。 | ☐ |
| 3 | **节奏感** | 长短句交替使用。数据段落（数字密集）后接解释性段落缓口气。连续三句以上同长度句式则需调整。 | ☐ |
| 4 | **过渡自然** | 章首不用「值得一提的是」「值得注意的是」「此外」等拐杖词。直接给数字或场景推进。章末有自然悬念指向下一章。 | ☐ |
| 5 | **专业概念随文解释** | 首次出现的缩写/术语必须在正文中用一句话解释清楚（或使用 `.term[data-tip]`），不能在开头堆术语表。 | ☐ |
| 6 | **隐喻克制** | 全篇只使用一个与标题一致的核心隐喻。清除草稿中与标题打架的其他隐喻。固定用语（城市/护城河等）不是隐喻杂音，勿误伤。 | ☐ |
| 7 | **无媒体自称** | 全文不得出现「本报」「本刊」「本社」「本台」等字样。统一用中性「调查团队」。 | ☐ |
| 8 | **虚构引述检查** | 不得出现「XX向调查团队表示」——我们没有进行实际采访。真实来源才引述。 | ☐ |
| 9 | **数字表达** | 同一篇文章内数字单位统一（亿/万），百分比精确到小数点后一位。多单位混用（金额+百分比）需注明。 | ☐ |
| 10 | **标题吸引力** | 标题是否基于该主体独有矛盾？读完后读者是否想继续看下去？是否与其他篇的标题有明显区隔？ | ☐ |

### B. 图表审核

逐项检查，全部通过方可发布：

| # | 检查项 | 标准 | 通过 |
|---|--------|------|------|
| 1 | **表格完整渲染** | 所有 `<table>` 在手机端（375px 宽）无溢出、列不错位、单元格无截断。在桌面端也正常。 | ☐ |
| 2 | **SVG 图表渲染** | 环形图（`.donut-interactive`）、柱状图、曲线图在移动端和桌面端均正常显示，入场动效正常。 | ☐ |
| 3 | **数据可溯源** | 每张图表/表格的数据来源能在脚注中找到对应编号。不臆造结构性拆分。 | ☐ |
| 4 | **脚注一一对应** | 正文 `<sup>[N]</sup>` 与文末 `.footnotes ol li` 数量一致、编号匹配。使用 `combined` 正则拆分防呆（将 `[1][3]` 拆为独立 `<sup>`）。 | ☐ |

## GitHub Pages 同步纪律

本门站已迁移至 GitHub Pages（仓库 `szsyqq/DeepInvestigationLab`），`git push` 后 GitHub Actions 自动将 `portal/` 部署到 Pages。

**同步流程**：
1. 在本地完成修改并部署到 CloudStudio 沙箱预览
2. **等待用户刷新确认无误后**，询问用户是否推送到 GitHub Pages
3. 用户确认后，执行推送（GitHub Actions 自动完成部署）
4. **严禁**在未获用户确认的情况下直接推送

### Git Push 失败时的 API Fallback

沙箱环境的 HTTPS 代理隧道偶尔不稳定（返回 502 "CONNECT tunnel failed"），此时 `git push` 不可用，但 `gh api`（REST API）通常仍能正常工作。

**检测方法**：`git push` 报 "CONNECT tunnel failed, response 502" 时，先验证 API 是否畅通：
```bash
gh api repos/szsyqq/DeepInvestigationLab --jq '.name'
```
如果返回仓库名，说明 API 可用，按以下步骤通过 API 推送：

```bash
# 1. 找出当前 main 的最新 commit SHA
LATEST=$(gh api repos/szsyqq/DeepInvestigationLab/git/refs/heads/main --jq '.object.sha')
# 2. 获取该 commit 的 tree SHA
TREE=$(gh api repos/szsyqq/DeepInvestigationLab/git/commits/$LATEST --jq '.tree.sha')
# 3. 将需要推送的 file base64 编码，创建 blob
BASE64=$(base64 -i <file_path>)
BLOB=$(echo "{\"content\":\"$BASE64\",\"encoding\":\"base64\"}" | gh api repos/szsyqq/DeepInvestigationLab/git/blobs --input - --jq '.sha')
# 4. 创建新 tree（含更新后的文件）
NEW_TREE=$(echo "{\"base_tree\":\"$TREE\",\"tree\":[{\"path\":\"<repo_relative_path>\",\"mode\":\"100644\",\"type\":\"blob\",\"sha\":\"$BLOB\"}]}" | gh api repos/szsyqq/DeepInvestigationLab/git/trees --input - --jq '.sha')
# 5. 创建 commit
NEW_COMMIT=$(echo "{\"message\":\"<commit_message>\",\"tree\":\"$NEW_TREE\",\"parents\":[\"$LATEST\"]}" | gh api repos/szsyqq/DeepInvestigationLab/git/commits --input - --jq '.sha')
# 6. 更新 main 分支引用
echo "{\"sha\":\"$NEW_COMMIT\",\"force\":true}" | gh api repos/szsyqq/DeepInvestigationLab/git/refs/heads/main -X PATCH --input -
```

**关键变量替换**：
- `<file_path>` — 要推送的本地文件路径（如 `portal/reports/fund-gray/index.html`）
- `<repo_relative_path>` — 在仓库中的路径（如 `portal/reports/fund-gray/index.html`）
- `<commit_message>` — 提交信息

**注意事项**：
- API 推送会绕过本地的 git 历史记录，推送后本地 `git pull` 会提示分叉——这不是错误，这是正常现象。用 `git fetch --all && git reset --hard origin/main` 同步本地即可
- 不适合批量推送多个文件的情况（每次只能更新一个文件）
- 推送后 GitHub Actions 部署流程跟正常 `git push` 完全一致

## 门户生成：数据驱动机制（v7 增设）

> **2026-07-24 启用**。从此 `portal/index.html` 不再手动编辑，由脚本从 JSON 数据源自动生成。

### 为什么改为数据驱动

以前手动编辑 `portal/index.html` 的卡片区域，频繁出现：
- 新增文章误删或改写已有卡片的描述
- 卡片顺序错乱（最新不在最前）
- 试读标签遗漏
- 侧边导航编号与卡片顺序不对应

### 新增/修改文章的发布流程

1. **写底稿** → 复制到 `portal/reports/<key>/`
2. **编辑 `portal/reports.json`**：
   - **新增文章**：在最前面加一条记录（date=今天，title/desc/tags 等）
   - **修改已有文章**：将其 `date` 改为今天（自动排序到首页最上面），同时在文章页面的 masthead 区加「修订于 YYYY-MM-DD」标记
3. **运行生成脚本**：
   ```bash
   python3 scripts/build-portal.py
   ```
   → 自动更新 `portal/index.html`（20+ 张卡片 + 导航 + 编号全部自动生成）
4. **部署预览** → 用户确认 → 推送 GitHub Pages

### `reports.json` 记录格式

```json
{
  "id": "xxx",
  "date": "2026-07-24",
  "co": "公司名",
  "tags": ["标签1", "标签2"],
  "trial": true,
  "title": "报告标题",
  "desc": "卡片描述文本",
  "readingTime": "约 N 分钟阅读",
  "navShort": "导航短标题"
}
```

- `trial: true` → 自动加「试读」标签
- 卡片按 date 降序排列，同日期按 JSON 顺序
- 导航编号自动从 01 开始递增

### 纪律

- **严禁** 直接编辑 `portal/index.html` 的卡片区域——会被脚本覆盖
- 改导航/卡片模板 → 改 `portal/template.html` 和 `scripts/build-portal.py`
- 增/删报告 → 只改 `portal/reports.json` + 运行脚本

## 数据获取：必须执行的渠道清单（v6 增设）

> **纪律**：每篇报道必须完成下方至少 3 个渠道的数据采集，不得仅凭东方财富 API 的摘要数据（RPT_LICO_FN_CPD）就开写。每个渠道采集到的原始资料保存到 `底稿/日期_公司/原始资料/{舆情网页,招股书年报,研报数据}/`。

### 渠道 A：境内上市公司（含 A 股/港股中资）

| 证监会/交易所问询函 | 巨潮资讯网(cninfo) WebFetch | 监管质疑+公司回复，具深度细节 | ⭐⭐⭐ |
| 公司招股书全文 | 巨潮资讯网/交易所官网 | 历史沿革、股权、业务拆解 | ⭐⭐⭐ |

| 信用评级报告 | 中诚信/联合资信官网 | 债券发行人详细财务分析 | ⭐⭐ |

| 数据源 | 获取方式 | 内容 | 优先级 |
|--------|---------|------|--------|

| **SEC EDGAR Proxy / 8-K** | 同上 | 重大事项、股权结构 | ⭐⭐ |

| 行业研究报告（STR/CBRE） | WebSearch + WebFetch | RevPAR、供给趋势、竞争格局 | ⭐⭐ |

### 渠道 C：非上市/集团子公司（如平安证券）

| 数据源 | 获取方式 | 内容 | 优先级 |
|--------|---------|------|--------|
| **债券募集说明书** | 中国债券信息网(chinabond)/上交所债券公告 | 详细财务数据（营收、负债、现金流） | ⭐⭐⭐ |
| **信用评级报告** | 中诚信/联合资信官网 | 行业地位、财务分析、风险因素 | ⭐⭐⭐ |
| 母公司年报分部报告 | 母公司 RPT_LICO_FN_CPD | 集团内该子公司的收入/利润拆分 | ⭐⭐ |
| 行业排名数据 | 证券业协会/酒店业协会 | 市场份额、排名变化 | ⭐⭐ |

### 渠道 D：通用渠道（所有类型）

| 数据源 | 获取方式 | 内容 | 优先级 |
|--------|---------|------|--------|
| **WebSearch** | 多关键词搜索 | 最新新闻、行业数据、竞争对手信息 | ⭐⭐ |
| **WebFetch 快照保存** | 对关键页面存 .html | 舆情、分析文章、官方公告（防失效） | ⭐⭐ |

### 执行纪律

1. **调用东方财富 API 时，如果查询字段不生效，必须尝试不同的 RPT 表名和字段名组合，不可放弃**
2. **API 基线数据拿到后，必须至少再从渠道 A/B/C 中选 2 个执行，存档到 `原始资料/`**
3. **每条脚注对应的数据来源，需在 `原始资料/` 中有对应文件或 URL 快照**
4. **如果网络不可用（WebSearch/WebFetch 均失败），在资料清单中标注「待补充」并记录原因**

## 评估团研讨（v6 增设）

> **红线**：所有材料收集完毕后，不得直接进入写作。必须先经过评估团研讨，输出《追问清单》后方可动笔。

### 为什么要有这一步

过去几篇文章（平安证券、希尔顿、五粮液等）的反馈暴露了一个问题：材料收集齐全后直接套用网上公开报道的叙事框架，导致文章沦为"出处汇编"，缺乏独立判断和读者视角的穿透力。评估团的作用，是在动笔之前强制建立一个**观点蒸馏**环节。

### 评估团怎么运作

评估团不是真实人物集体讨论，而是**由一个 AI 扮演全部角色**，依次完成以下三轮思考并输出书面记录，并存档到底稿的 `原始资料/` 目录：

#### 第一轮：读者视角（"普通关注者"）
问自己：如果我是一个对这家公司没什么了解的普通人，我看到这些材料后会关心什么？
- 这家公司最让我意外的数字是什么？
- 它的业务模式用一句话怎么讲？
- 它跟我的生活有什么关系？
- 读完材料我最大的疑惑是什么？

产出：<code>原始资料/评估团_读者视角.md</code>

#### 第二轮：市场视角（"投资者/分析师"）
问自己：如果我是一个持币待投的投资者，这份材料中哪些信息最影响我的判断？
- 市场对这个公司的共识是什么？（机构观点、券商评级）
- 共识有没有值得质疑的地方？
- 哪些风险被市场低估了？哪些利好被夸大了？
- 它的估值/业绩背后的驱动因素有哪些是可持续的？哪些是一次性的？

产出：<code>原始资料/评估团_市场视角.md</code>

#### 第三轮：争议视角（"质疑者"）
问自己：如果我是一个对这个公司持怀疑态度的批评者，我会抓住哪几个点不放？
- 公司最不喜欢外人讨论的话题是什么？
- 它的公开说法和实际数据之间有没有裂缝？
- 监管/媒体/行业对手提出了哪些公司不愿正面回答的问题？

产出：<code>原始资料/评估团_争议视角.md</code>

### 三轮整合

读完三份评估团产出后，提炼出 **3-5 个"真正值得追问的问题"**，这些问题将成为后续定论点、搭骨架的核心材料。每个问题必须满足：
1. **有数据支撑**——不是空洞的猜想，材料中能找到具体数据来回答
2. **有张力**——公司说法 vs 市场看法之间存在裂缝
3. **有读者价值**——普通读者读完后会觉得"我之前没想到这一点"

产出：<code>原始资料/评估团_追问清单.md</code>

### 评估团禁做
- ❌ 不能用来"确认已有观点"——评估团的目的是质疑，不是背书
- ❌ 不能用来挑选"好写"的角度——好写不等于读者关心
- ❌ 禁止直接搬运网上评论作为评估团观点——各轮思考必须基于已收集的原始资料，结合 AI 自身分析能力
- ❌ 评估团不预设结论——它的任务是列问题、不是给答案

## 篇章深度要求（对标参考文章）

> 2026-07-22 用户反馈：近期文章（五粮液/希尔顿/平安证券）篇幅仅为参考文章（宇树/小红书/周生生）的 30-60%，数据密度和论证深度明显不足。
> **根因**：仅用 API 摘要数据 + 单层论证（只呈现不交叉验证），未使用原始文档级数据（10-K/招股书/评级报告）。

### 字数与章节硬指标

| 维度 | **最低要求** | 参考文章基准 |
|------|------------|------------|
| 正文纯文本字数 | **≥ 8,000 字** | 小红书 8,531 / 周生生 12,656 / 宇树 22,382 |
| 阅读时间 | **≥ 15 分钟** | 小红书 18 分钟 / 周生生 26 分钟 |
| 章节数 | **≥ 8 章**（含导语+尾声） | 宇树 9 / 小红书 8 / 周生生 12 |
| 脚注数 | **≥ 15 条** | 小红书 17 / 周生生 40 / 宇树 39 |
| 图表/表格数 | **≥ 7 个** | 每章至少 1 个数据载体 |
| 数据源渠道 | **≥ 3 个** | 宇树用了招股书+问询函+舆情+研报 |

### 每章展开模板

每章必须执行「呈现-对照-数据」三层骨架，不得只做第一层：

1. **呈现**：抛出一个具体数字或事实（如"营收下降 54.55%"）
2. **对照**：给出另一种解读或公司说法（如"公司声称是行业周期" vs "竞争对手只跌了 1.2%"）
3. **数据落点**：用第三方数据交叉验证（如"多家券商估算渠道库存 XXX"），回扣章标题

**单章正文至少 800 字**（参考文章单章平均 1,000-2,000 字）。如果写到 600 字就感觉"没东西可写了"，说明数据获取不够，需要回退到数据采集阶段补充渠道。

## 页面排雷：CSS/JS 底层技术细节

> 本节的 CSS 像素值、路径计算源自历史踩坑，新页面必须逐条核验。

### 顶部三元素联动（最高频重叠源）
- `.internal-banner` 高度约 33px（padding 8+8 + font 12px × ~1.4 行高）→ `.top-bar` 必须以 `top:33px` 定位 → `body{padding-top:76px}` 必须等于 banner(33px) + top-bar(~40px，含 9+9 padding + 22 行高 + 1px 底边框)。
- **三个值是联动硬编码**：改了任一个就必须同步更新其余两个。签名检查：浏览器实测滚动前 banner 与 top-bar 相邻无缝。
- `.compact` 模式（滚动后）：`.compact .top-bar{top:0}` + `.compact .internal-banner{display:none}` + `.compact .progress-bar{top:30px}`。窄屏下 `top:28px`。
